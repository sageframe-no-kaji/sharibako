# ho-06.10 — Protect

The second build ho of the kamae-2.3 arc. "Identify secrets" becomes real:
when a `.env` is read, every line is classed as a **secret** or a
**setting** before the user sees it, by one rule in the engine that both the
CLI and the Workshop use. The rule only sets defaults. The review screen is
never skipped, lists every line including settings, and lets any line be
flipped (kamae-2.3 §4, ratified with that exact change). Then bulk protect:
every unprotected project in one review, one Touch ID.

**Out of scope:** the vocabulary sweep (06.11); multi-root management
(06.6); linking (ho-07).

---

## Phase 1 — Think

### Decision 1 — The rule lives in Core as `SecretClassifier`

A pure, dependency-free type in `SharibakoCore`. Input: key, value, and
whether the key name-matches a shared entry. Output: `.secret(reason)` or
`.setting(reason)` with a named reason the review screen can show as a
tooltip ("looks like a port number", "key ends in _SECRET"). Deterministic,
unit-tested against a corpus of real-shaped `.env` lines.

### Decision 2 — The rule, in order (amends kamae-2.3 §4 rule 4)

1. The key name-matches a shared entry already in the vault → **secret**,
   with the shared ID as the suggested link.
2. Key shape → **secret**: the uppercased key ends in `KEY`, `SECRET`,
   `TOKEN`, `PASSWORD`, `PASSWD`, `CREDENTIALS`, `CREDS`, `DSN`, `PRIVATE`,
   or contains `API_`, `AUTH_`, `_AUTH`, `PRIVATE_KEY`, `ACCESS_KEY`,
   `SIGNING`, `WEBHOOK`.
3. Value shape → **secret**: a URL whose authority carries user info
   (`scheme://user:pass@…`); a PEM block (`-----BEGIN`); a JWT
   (`xxx.yyy.zzz` base64url segments).
4. Value shape → **setting**: a boolean (`true/false/yes/no/on/off/0/1`,
   case-insensitive); a number (integer or decimal, optional sign); a
   filesystem path (`/`, `~`, `./`, `../` prefix) with no `@`; a bare
   hostname or `host:port` (`localhost`, `db`, `redis:6379`); a URL with no
   user info and no query string; an enum-looking word (letters, digits,
   `-`/`_`, at most 24 chars, not matched by rule 2); an empty value.
5. Otherwise → **secret**. *This is the amendment.* kamae-2.3 §4 wrote the
   fallback as "setting"; a value Sharibako does not recognise as a plain
   setting is protected by default, because the cost of a wrong "setting"
   is a secret left in plain text, and the cost of a wrong "secret" is a
   config value in the vault. The user flips either on the review screen.

No entropy threshold: rule 4's shapes cover what settings look like; what
remains is protected. Recorded in Reflect for the practitioner's veto.

### Decision 3 — Both surfaces use the rule for defaults, never for decisions

CLI `init`: the prompt lists every line with its class before asking, and
the one-key default becomes "Protect N secret(s), leave M setting(s) alone?
[Y/n]". Under `--yes` (non-interactive) the defaults apply and each line's
class is printed, because scripts cannot look. Workshop: 06.9's per-project
sheet defaults from the rule in this ho's AT-02, and the bulk review screen
replaces it.

### Decision 4 — Tags are free text with suggestions

`ScopeType` becomes a string-backed `ScopeTag` with the five existing raw
values kept valid and four suggestions (`dev`, `prod`, `service`,
`machine`). No vault migrates. Protect no longer asks for a tag; it is an
optional field on the project page. (AT-02 or AT-03.)

### Decision 5 — Bulk protect, one review, one Touch ID (reshaped by D6)

Superseded in shape by Decision 6: there is no separate review screen. The
project page is the review. "Protect N secrets" on a page commits that
project's recommended lines through `acceptIngest` behind one Touch ID;
"Protect all" in the Not-protected section header does the same for every
unprotected project inside one key handle (the Check-all pattern). Choosing
a folder outside the roots registers its root (shipped in 06.9's gate fix:
New… › Protect a folder…). Attaching a folder to a no-folder project writes
the claim file (`Materializer.writeMarker`).

### Decision 6 — One project page, protected or not (06.9 gate, 2026-11-08)

Supersedes ho-06.9 Decision 9 and the separate Not-protected page. A project
is a set of `.env` lines; each is in the vault or not. The page shows the
lines with that fact on each one, whatever the project's overall state:

- **Header.** Name, folder. When any secret is unprotected: a large red
  mark (`xmark.octagon.fill` in the alarm token), "N secrets not protected",
  and one button **Protect N secrets**. When all are protected: the green
  check, "Protected", and the up-to-date clause when known. For a folder the
  vault does not know yet (today's candidate), the same header — the project
  simply has zero protected lines.
- **Lines.** Secrets first, each with a status mark: green lock = protected
  (in the vault); red open lock = not protected (in `.env` in plain text, the
  classifier says secret); grey = in the vault but missing from `.env`.
  Then a quiet divider and the **settings**, dimmer, collapsible to one row
  ("7 settings left in .env"). Every line shows its recommendation and
  reason in caption text ("secret — key ends in KEY").
- **Detail pane.** A protected line: today's `SecretDetail` (value behind
  Reveal, notes, history, delete). An unprotected line or a setting: the
  plaintext value as it stands in the file, the class and reason, and the
  choice for this line (Decision 7), with **Protect this line** as the
  action when the choice protects.
- **No sheet.** `IngestSheet`, `NotProtectedPage`, and the Scope ID / Scope
  type prompts go. A new project's ID is the folder name (suffixed on
  collision); its tag is optional and set later on the page (Decision 4).

### Decision 7 — Four choices, in plain words, defaulted by the classifier

Per line: **Protect for this project** (`importAsLocal`), **Use shared
secret ‹name›** (`linkToShared`; offered when a shared secret exists, the
name match preselected), **Make it a shared secret** (`moveToShared`),
**Leave in .env as a setting** (`leaveAlone`). `skip` collapses into the
last — a user cannot tell them apart. The default is the classifier's
class: secret → Protect for this project (or Use shared ‹name› on a name
match), setting → Leave in .env. The user flips any line; flips are
remembered for the session.

### Decision 8 — The verbs the gate asked for

- **Unprotect** (project): make sure every owned value is in `.env`
  (materialize, refusing on drift as today), delete the vault entry, remove
  the claim file; the row drops to Not protected. Rust, confirmed.
- **Right-click menus** on project rows and on lines, mirroring the action
  column's verbs for that thing.
- **Use shared secret…** / **Make it a shared secret** on an already
  protected line (`VaultCore.link` / `addSharedEntry` + `link`), so a secret
  protected locally by accident can be moved afterwards.
- **Check all** continues past a project it cannot read and reports per
  project ("4 checked · 1 out of date · 2 could not be read"), and notices a
  local value equal to a shared secret's value (it already decrypts both),
  offering the link on that line.
- **Remote…** (VAULT): set or change the vault's git remote
  (`Conduit.setRemote`), shown in the footer.
- **Scan folders…** (VAULT): the list of scan roots with Add and Remove,
  persisted to `config.yaml`; Rescan follows. This is ho-06.6's core, pulled
  in because the practitioner needs it now; 06.6 keeps the per-vault vs
  per-Mac roots decision.
- **Errors where the action was.** A failure from a pane's action renders
  in that pane (inline, alarm token) with a next step ("Delete this project
  and protect the folder again, or switch to the key that made it"); the
  status bar keeps the one-line echo.

### Decision 9 — Core additions allowed in this ho

`VaultCore.getSharedValue(_:)` (read one shared entry, for the value match
and for the shared page), and whatever `acceptIngest` needs to add lines to
an existing project without re-asking for ID and type (it already
reconciles). Nothing else in Core; the CLI gains no verbs here.
